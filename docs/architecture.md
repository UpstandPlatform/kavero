# Kavero architecture

Bun + Turborepo monorepo. One deployable app (`apps/web`, Next.js 16 App Router) built from TypeScript workspace packages that Next transpiles directly (`transpilePackages`); there is no separate package build step.

## Packages

| Package | Role | Runs in |
| --- | --- | --- |
| `catalog-engine` | The canonical document model: Zod schema (`schema.ts`), factories/templates (`document.ts`, `templates.ts`), parsing + migration + integrity checks (`validation.ts`), HTML/CSS sanitising (`sanitize.ts`). Everything else depends on it. | anywhere |
| `editor-core` | Framework-agnostic editor: every change is an `EditorCommand` applied by `applyCommand`; `Editor` keeps undo/redo history (with coalescing), selection and a `dirty` flag that drives autosave/sync. | anywhere |
| `animation-engine` | Deterministic animation runtime: element animations and slide transitions as pure functions of time, so editor preview, published site and frame-by-frame video match. | anywhere |
| `renderer` | React components that draw a document: `SlideView`, `FrameView` (one frame at time *t*), `Presentation` (published viewer), font loading. | browser / SSR |
| `local-storage` | Local-first persistence: `CatalogRepository` over IndexedDB (documents, assets, summaries, cloud link/sync state) and the `.kavero` project file (JSON envelope with base64 assets). | browser |
| `export-chromium` | Headless Chrome (playwright-core) exports: PDF, PNG slide images, MP4/WebM video (frames piped to ffmpeg). Loads the app's `/render` page. | server |
| `export-pptx` | Editable PowerPoint export: elements map to native text boxes, shapes and pictures. | browser |
| `ai` | LLM providers (Anthropic, OpenAI-compatible) and the plan → build / edit flows that produce documents or editor commands. | server |
| `db` | Drizzle schema + migrations for Postgres: auth tables, `catalog` / `catalog_revision` / `catalog_asset`, `publication` / `publication_asset`, `api_token` / `audit_log` / `mcp_connection`, `ai_job`. | server |
| `api` | tRPC routers (`catalog`, `publication`, `integrations`, `ai`) over services that hold the business rules (`CatalogService`, `PublicationService`, `TokenService`, `McpConnectionService`, `AiService`, SSRF-safe fetch, `SecretBox`). | server |
| `auth` | Better Auth factory (`createAuth(env, db)`), email + password, Drizzle adapter. | server |
| `mcp-server` | `createKaveroMcpServer(principal, host)`: MCP tools for catalogs, slides, elements, themes, animation, product import, preview and publishing, built on the same services and editor commands. | server |
| `ui` | Shared shadcn-style components, hooks and styles. | browser |
| `config` | Shared tsconfig. | — |

## apps/web

- `src/app` — routes: `/` (landing), `/dashboard`, `/editor/[catalogId]`, `/settings`, `/login`, `/c/[slug]` (published site, password gate, assets, OG image), `/render` (headless frame host for exports), `sitemap.ts`, `robots.ts`.
- `src/app/api` — `auth/[...all]` (Better Auth), `trpc/[trpc]`, `catalogs/[id]/assets/[assetId]` (asset upload/download), `export/pdf`, `export/video` (job queue), `mcp` (Streamable HTTP MCP endpoint, bearer API tokens), `health`.
- `src/modules`
  - `catalog` — dashboard, local catalog access (`local-catalogs.ts`), cloud push/pull with conflict handling (`cloud-sync.ts`), thumbnails.
  - `editor` — editor shell, canvas, properties panel, preview player, export/publish dialogs, product import, `use-catalog-editor` (binds `editor-core` to React + IndexedDB) and `use-cloud-autosync`.
  - `export` — export access checks and the in-memory video job queue (max 3 concurrent, files in OS temp dir).
  - `publishing` — loading publications for `/c/[slug]` with visibility/password rules.
  - `settings` — account, API tokens, MCP connections.
  - `storage` — `ObjectStorage` (`put/get/delete`): `FileSystemStorage` (default) or `S3Storage` (S3/R2/MinIO), chosen by `STORAGE_DRIVER`.
- `src/services.ts` — the process-wide `db` and `auth` instances; `src/env.ts` is generated by varlock from `.env.schema`.

## Document model

A catalog is a single JSON `CatalogDocument` (`catalog-engine/src/schema.ts`, `schemaVersion` 1):

```
CatalogDocument { id, schemaVersion, revision, metadata{title, language, currency…},
                  settings{width, height, background}, theme{colors, fonts},
                  slides[] { id, name, background, transition, elements[] },
                  assets[] { id, name, mimeType, hash… }, products[] }
Element = text | image | shape | product | product-grid | icon | video | button | html
          (common: position, zIndex, locked, hidden, opacity, groupId, animations[])
```

- Pure data: rich text is stored as runs, animations as declarative presets/keyframes, colours/fonts may be theme tokens (`token:primary`). `html` elements are sanitised.
- Assets are referenced by id; bytes live in IndexedDB locally and in object storage (`catalogs/<rowId>/<sha256>`) in the cloud.
- All writes go through `parseCatalogDocument` / integrity checks; every editor change is an `EditorCommand`, which is also what the AI edit flow and MCP tools emit.

## Local-first + cloud sync

1. Catalogs are created and edited in the browser and saved to IndexedDB (`local-storage`); the app works signed-out.
2. Signed-in users can push a catalog to the cloud (`catalog.save`). The server stores the document in `catalog` (JSON), bumps `revision` and keeps the last revisions in `catalog_revision`.
3. Optimistic concurrency: each push sends `baseRevision`; if the cloud copy moved on, the server returns a conflict and the client offers "keep mine" (force) or "take cloud".
4. Asset bytes are uploaded separately (`PUT /api/catalogs/:id/assets/:assetId`, content-addressed by SHA-256) after the document references them.
5. Autosync (`use-cloud-autosync`) pushes dirty, linked catalogs in the background. A cloud link is bound to the user id so another account never syncs it.

## Publishing

`PublicationService.publish` snapshots the current cloud document into `publication.document` and pins its assets in `publication_asset`, so later edits don't change the live site until republished. Each catalog has at most one publication with a unique `slug` and a visibility: `public` (listed in the sitemap), `unlisted`, `password` (hashed, unlocked via cookie) or `private`. `/c/[slug]` renders with `renderer`'s `Presentation`; `/c/[slug]/og` renders a social image with headless Chrome and caches it in object storage (`publications/<id>/og-v<n>.png`).

## Exports

- PDF, PNG previews, video: `export-chromium` opens `/render` in headless Chrome at the request's origin, injects the document, steps `animation-engine` frame by frame, and (for video) pipes frames to ffmpeg.
- PPTX: generated client-side by `export-pptx`.
- `.kavero` project file: `local-storage/project-file.ts`.

## MCP

- **Kavero as an MCP server**: `POST /api/mcp` exposes `mcp-server` tools to external agents. Auth is a bearer API token (`api_token`, hashed, scoped `catalogs:read|write|delete` + `publish`), rate-limited per token in memory, every call written to `audit_log`. Tools operate on cloud catalogs through the same services and editor commands as the UI.
- **Kavero as an MCP client**: users register external MCP servers (`mcp_connection`, credentials encrypted with `SecretBox`, key derived from `BETTER_AUTH_SECRET`) and call their tools from the editor's product import to pull product data into a catalog.
